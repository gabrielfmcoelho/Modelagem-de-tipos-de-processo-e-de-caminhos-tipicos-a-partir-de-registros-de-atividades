# Experiment Arms and Run Identifiers

The study is a matrix, not a single run. The same corpus is processed under two
identity treatments, clustered by three algorithms under five parameterisations,
and each real result is paired with a shuffled null. The run-id convention is
what keeps those cells addressable, and it is enforced by the directory layout
rather than by documentation alone.

## The convention

A run id is compositional:

```
exp-<arm>[-<parameterisation>]
```

The two arms are `exp-raw` and `exp-anon` — the same processes represented from
raw document text and from anonymized text respectively. Parameterisations append
a suffix: `exp-raw-ksil`, `exp-anon-hcoarse`, `exp-anon-cut0.5`. The control
suffix `-shuffled` composes on top of any of them, producing ids such as
`exp-anon-kelbow-shuffled`.

The artifact path is:

```
artifacts/<domain>/<run_id>/<algo>/
```

**The algorithm is the level below the run id, never part of it.** This is the
single rule that makes the matrix traversable: a run id names an experimental
condition, and every algorithm applied to that condition lives underneath it.
`artifacts/clustering/exp-anon/` holding `hdbscan/`, `kmeans/`, `leiden/` and a
run-level `selection.json` is the shape all consumers assume.

Opaque identifiers naming a semester or a milestone were deliberately removed
from the repository; a run id must describe the condition it names.

## Artifact domains

`artifacts/` is partitioned by what a file *is*, not by which stage wrote it:

| Domain | Holds |
|---|---|
| `features/` | Per-arm feature matrices, one `.npz` per arm |
| `clustering/` | Partitions, per run id then per algorithm |
| `typical/` | Typical-path evaluation cells, plus the run manifest |
| `traces/` | Exported event traces per run id |
| `stats/` | Cross-cutting statistics such as the ablation summary |
| `runs/` | Per-stage execution ledger entries |
| `cache/` | Reusable intermediates |

`pipeline/evidence/shared/paths.py` centralises the roots that evidence code
resolves against, together with the `-shuffled` suffix constant and
`MAIN_CELLS` — the six primary cells formed by the two arms crossed with the
three base algorithms.

## The cell matrix

`pipeline/stages/matrix.py` declares the full evaluation grid.
`REAL_CELLS` enumerates fourteen `(run_id, algo)` pairs: the two arms crossed
with the three base algorithms, plus each arm's four parameterised variants
(`kelbow`, `ksil`, `lres`, `hcoarse`) paired with the algorithm they
parameterise. `CELLS` then doubles that set by appending the shuffled suffix to
every run id, giving twenty-eight cells. Each cell is evaluated once per
alphabet, and the stage documents the resulting scale — eighty-four cells, on the
order of a day of compute.

Because the shuffled cells are generated by transforming the real cell list
rather than being listed separately, a new real cell automatically acquires its
control. The pairing cannot drift.

## Building an arm

`build-arm` is the macro that produces one complete arm. It requires
`--flag run_id=…` and raises `ValueError` naming the expected values when it is
absent — there is no default arm, because silently building the wrong one would
be worse than failing.

Its sequence is: build features for the arm (or reuse an existing feature file
when `skip_embed=true`, which is validated to exist first), sweep parameters with
`select-k`, then run five clusterings — the base configuration plus the four
parameterised variants — followed by stability analysis and the cluster audit.

The parameter values for the four variants are not hard-coded. `build-arm` reads
`selection.json` written by `select-k` and pulls `k_elbow`,
`k_best_silhouette` and `best_resolution_combined` out of it, failing with a
clear error if that file is absent. It also inspects the selection's
`at_grid_edge` map and warns that the sweep should be widened before the arm is
trusted when a chosen value sits at the boundary of the searched range — a
selection at a grid edge is evidence the true optimum lies outside it.

`build-arm` declares `deterministic='conditional'` with the reason that it
inherits the determinism of each sub-stage it runs.

### Two macro patterns

The repository composes stages in two distinct ways, and the difference matters
when reading the DAG.

`etl` and `etl-full` compose **through the registry**: they declare
`depends_on` and do nothing themselves, so the runner resolves and checkpoints
each constituent stage normally.

`build-arm` and `ablation` compose **by direct call**: they construct a fresh
`RunContext` carrying different flags but the same writer, reader and driver, and
invoke the sub-stage module's `run` function directly. This bypasses the registry,
the topological resolution and the per-stage checkpointing, which is precisely
why it is used — the same stage must run several times within one macro under
different flags, something the checkpointing model would otherwise collapse into
a single cached execution. Both macros consequently declare
`can_skip_when_done=False`.

The two differ in one detail: `build-arm` passes `ctx.cache` straight through, so
sub-stages share the run's memoised values, while `ablation` passes a separate
cache dictionary, isolating each variant's computations from the shared run
state.

## Controls and ablations

Two stages generate the comparison conditions the evidence phase needs.

**`cluster-control`** builds the null partition. `shuffle_labels` sorts processes
by protocol, permutes the label values across them with a seeded RNG, and
reassembles the mapping. Permuting values rather than reassigning them at random
**preserves both the number of clusters and the distribution of cluster sizes**,
so a comparison against this control isolates the contribution of *which*
processes were grouped together from the contribution of merely having that many
groups of those sizes.

The seed defaults to 42 and is recorded in the artifact's provenance parameters,
so the control is reproducible despite being pseudo-random — the stage declares
`deterministic='conditional'` on exactly that basis. It refuses to proceed when a
source partition is missing, telling the operator which `cluster-eval` to run
first, and raises when a shuffle turns out to be a no-op rather than emitting a
control identical to its source. Output goes to
`<run_id>-shuffled/<algo>/labels.json`, stamped with the source cell as a hashed
input.

**`ablation`** measures feature-block and temporal-cutoff contributions. Its
default variants disable feature blocks (`nokeyword`, `notopic`) or truncate each
process's history to a fraction of its length (`cut0.75`, `cut0.5`, `cut0.25`).
Each variant is named as `name:flag=value` and rejected if it does not parse that
way. For each, features are rebuilt, the processes re-clustered, and the result
compared against the reference partition using adjusted Rand index and normalised
mutual information over the processes the two partitions share, refusing to
report anything when the intersection is empty. Cluster counts exclude the `-1`
noise label, which HDBSCAN assigns to unclustered points, while noise counts are
reported separately.
